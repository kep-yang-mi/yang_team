# 루브릭 — 급여 담당 옹호자 (`persona-advocate:payroll`)

## 렌즈
"이번 달 급여를 **누구에게, 어떤 구분으로** 지급하는지 마감 당일에 이 화면만 보고 확정할 수 있는가." 급여 담당은 매월 20~25일 사이 하루에 마감을 끝낸다.
화면은 마감 작업 순서(대상 확정 → 일할 → 휴직 → 계약 만료 → 오류 위험)대로 읽혀야 하고, **금액은 이 제품의 범위가 아니다**(GLOSSARY 제외 — HRIS 기능).
홈 제품은 Payroll Close(`payroll`)지만 세 제품 모두 채점한다: 홈이 아닌 제품은 "급여 마감 중 이 화면을 열 이유가 있는가"로 본다(0점이 아니라 재사용 가능한 부분을 평가).

## 공통 앵커 (모든 항목)
| 점수 | 뜻 |
|---|---|
| 0 | 해당 정보가 화면에 없다 |
| 3 | 있지만 핵심 필드가 빠져 마감에 쓸 수 없다(예: 대상 수만 있고 재직/휴직 구분 없음) |
| 5 | 마감에 쓸 수 있으나 급여 담당이 다른 파일을 열어 보완해야 한다 |
| 8 | 화면만으로 그 항목의 마감 작업이 끝난다 |
| 10 | 끝나고, 다음 행동(누구에게 무엇을 확인할지)까지 화면이 말해 준다 |

## 정성 항목
| id | 항목 | 필수 | 8점 조건 | 10점 추가 조건 | 근거 섹션(후보) |
|---|---|---|---|---|---|
| R1 | 월말 급여 대상 확정 즉시성 | must | 기준일·월말 급여 대상이 재직/휴직/합계로 있고, 월말 값이 예측(411)과 같음이 표시된다 | 고용유형별·조직별로 펼쳐지고 "예측과 일치" 배지가 있다 | `kpi`, `headcount` |
| R2 | 일할 계산 대상 완전성 | must | 당월 확정 입·퇴사자와 월말까지 예정 입·퇴사자가 **구분**되어 있고 근무일수·비율(3자리)이 있다 | 예정 건에 stale·already-separated 처리 표기가 있다 | `prorations-actual`, `prorations-planned` |
| R3 | 휴직 처리 구분 명확성 | nice | 무급(정부 급여)/유급/무급 3구분 집계 + 개인 목록(성명·조직·유형·시작일·처리) | 미확인 휴직유형(`기타`, unresolved)이 표에서 구별된다 | `leaves` |
| R4 | 계약 만료 선제성 | nice | 90일 내 만료 목록과 월별 건수(0 포함) | D-day 표기, 만료 경과 재직자 경고 | `contracts` |
| R5 | 오류 위험의 실행 가능성 | must | 위험 표에 사번·이슈·영향·플래그가 있다 | **어휘 구분**: 클린저 어휘(status-inconsistency 등) = "고객사 HR 확인 대기", 파생 어휘 = "급여 담당 즉시 확인"이 시각적으로 갈린다 | `risks`, `data-quality` |
| R6 | 마감 순서 가독성 | nice | 체크리스트가 상단, pending 먼저, 각 항목에 건수 | 체크리스트 항목이 해당 섹션으로 링크된다 | `checklist` |

제품 점수 = 6항목 평균(소수 1자리). must 항목이 3점 이하면 `mustFix`에 올린다.

## 홈이 아닌 제품을 볼 때
- Insight: `kpi`의 월말 인원·입퇴사 예정 건수·`planned-moves`(HR 뷰)는 R1·R2의 **참조용**이다(5점 상한 — 급여 대상 구분이 없다). `data-quality`는 R5에 부분 기여
- Onboarding: `timeline`의 입사 예정자(성명·일자·고용유형)는 R2의 예정 입사자 근거로 재사용 가능(5점 상한). 나머지 항목은 대개 0~3
- 이 점수들이 낮은 것은 결함이 아니다 — 통합 제품이 무엇을 `payroll` 탭으로 흡수해야 하는지를 말해 준다

## 실격 조건 (해당 시 제품 점수 상한 적용 + `mustFix`)
| 조건 | 상한 | 확인 방법 |
|---|---|---|
| 급여액·수당·계좌·세금 필드가 화면 또는 스냅샷에 있다 | 3 | `grep -niE '급여액|salary|amount|계좌|account|세금|tax' site/payroll/index.html site/data/payroll.json` → 0건이어야 |
| 생년월일이 화면 또는 스냅샷에 있다 | 3 | `grep -c birthDate site/data/payroll.json` → 0 |
| 월말 급여 대상이 예측 월말과 다른 값이다 | 5 | `payrollClose.payrollHeadcount.monthEndActive` vs `insight.json forecast.totals.forecastMonthEnd` |
| 이직 리스크 점수가 급여 화면에 있다 | 5 | `grep -c riskScore site/payroll/index.html` → 0 (급여와 무관, 등급조차 불필요) |

## must-have vs nice-to-have 요약
- **must-have**: R1 대상 확정 · R2 일할 대상 · R5 위험의 어휘 구분. 이 셋이 없으면 급여 담당은 이 제품을 열지 않는다(그 달 업무가 막힌다)
- **nice-to-have**: R3 휴직 · R4 계약 만료 · R6 순서. 없어도 마감은 끝나지만 다음 달 오류의 씨앗이 남는다

## note 작성법
점수마다 `note`에 근거 섹션(`data-section` 이름)과 무엇이 있었고 무엇이 빠졌는지를 한 문장으로. 예: `"prorations-planned에 예정 입사 19·퇴사 14가 있으나 workedDays 열이 없어 5점"`.
